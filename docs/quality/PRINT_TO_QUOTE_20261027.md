# Occasionally Odd print-to-quote workflow

Owner request: finish the Bambu capture workflow with actual outcomes, finishing time, hardware costs, reusable recipes, quantity quotes, delivery planning and a ten-completed-job accuracy sample. Owner-confirmed capacity: **one P2S and one P1S, 24 printing hours/day each; 2 hands-on finishing/packing hours/day**. Release build `phantom-live-20261027-246`.

## Product behavior

Production and Finance retain the existing Bambu feed, manual file analyzer, commerce records and saved models. Each captured file can seed a reusable recipe containing complete-product yield, hands-on minutes, nonprinted parts, packaging and explicitly compatible machines. Resliced files can be linked to the same recipe; matching names never silently merges products or establishes compatible Gcode.

A quantity quote rounds up to complete production batches and includes the material/time/failure allowance, hardware, finishing, packaging and payment assumptions. Matched saved inventory costs replace generic filament rates only under the existing exact identity and mass checks. The frozen quote records its source file, recipe version, material basis, rates, capacity calendar, quantity, cost thresholds and needed-by assessment. Recalculating creates a new immutable revision. Quote download is an internal draft; it does not send a customer message, publish a listing, reserve capacity, create an order or issue a print command.

The planner assigns full batches to compatible printers. P2S slice metadata does not automatically authorize P1S use. Recorded commerce work and explicit additional backlog reduce the calendar budget. An unassigned existing queue is conservatively budgeted against eligible machines. Calendar planning begins the next working day; finishing follows printing and excludes delivery transit. This is a conservative planned-ready date, not a precise earliest finish or guarantee. Unknown printer/finishing backlog keeps the ready date unconfirmed and may expose an explicitly conditional scenario. Draft quotes never reserve machines.

`server/scripts/configure-odd-print-capacity.ts --apply` applies only the owner's stated machine/day and hands-on budgets. It preserves other planning details and leaves unknown backlog unknown. It does not change printer hardware or commerce jobs.

## Actuals and ten-job measurement

Operator-confirmed outcomes are separately sourced from printer telemetry. Actual records retain consumed mass or explicit expenses, occupied time, finishing, hardware, packaging, actual revenue, fees and finished yield. Blank values remain unknown. Measured usage can be priced at the frozen confirmed rates; that cost basis stays visible. Quotes are not treated as sales or settled cash. Corrections retain the complete prior actual record. One finishing timer may run at a time; accumulated time survives refresh/restart and start/stop commands are idempotent.

The scorecard selects the most recent ten sufficiently measured completed jobs with an original pre-print quote, one complete matched batch, exact finished yield and positive actual manufacturing cost. A whole multi-batch quote cannot be compared to one captured print. Retrospective estimates, missing costs/time and incomplete yield are excluded with a reason. It reports absolute percentage cost-estimate error and recorded contribution per occupied printer-hour only where revenue/expenses are sufficient. Separate failed attempts and their known costs/hours remain visible and are not hidden inside a completed-job profit claim. Ten fixture outcomes prove the calculation, not ten physical production successes.

The workflow uses a separate bounded atomic `occasionally-odd-workflow.json` beside the existing print journal. Existing capture documents and archives are preserved. All commands carry an idempotency ID and expected revision; conflicting/reused command data fails safely. Business membership and owner/administrator authority remain mandatory for writes.

## Read-only printer status pairing

An independent **Printer completion** panel lets an Occasionally Odd administrator enter each printer's private IPv4 address, serial and normal eight-character LAN access code. No Bambu credential stores, encrypted logs or private keys are inspected. Newly provided credentials and network identity are encrypted at rest with AES-256-GCM using the existing runtime encryption secret; none are returned in HTTP responses or stored in browser persistence. Duplicate physical serials across the two slots are rejected. If server encryption is unavailable, pairing fails closed.

The existing API lifecycle starts the MQTT monitor only for configured connections. It subscribes to the exact `device/<serial>/report` topic over TLS, validates the bundled public Bambu CA and exact leaf serial identity, and exposes no publish/control operation. Certificate failure remains failure. The public CA is attributed and hash-verified in `server/resources/bambu-printer-ca.PROVENANCE.md`. Bambu's [authorization documentation](https://blog.bambulab.com/firmware-update-introducing-new-authorization-control-system-2/) distinguishes status push from protected control operations; no firmware downgrade, developer mode or security bypass is required by this implementation.

Printer outcomes require an explicit verified binding of a captured package to an exact physical-printer/task/subtask identity. A slot's physical binding ID changes with its serial, preventing a replacement printer from inheriting old task associations. Unmatched tasks remain unmatched, including LAN reports lacking a unique task ID. A percentage of100, zero remaining time, matching filename or nearby timestamp does not establish completion. Terminal status records the time completion/failure was observed; it does not invent actual print duration, material consumed or business costs. A paired status connection has not been physically verified until the owner's printer actually reports through it.
